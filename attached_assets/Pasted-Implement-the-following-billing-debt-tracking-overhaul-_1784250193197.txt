# PHASE 0 — Critical: stop the discharge PUT from nulling data

**Bug:** the "Régulariser" (resolve flagged discharge) action sends `PUT /api/discharges/:id` with body `{status:"settled"}` and no `statusOnly` flag. The backend's handler only does a safe status-only update `if (d.statusOnly)`; since that's never sent, every regularization falls into the full-overwrite branch and writes `undefined` into `truck`, `waste_type`, `gross`, `tare`, `net`, `unit_price`, `total`, `pay_method`, `site_id`, `ts`, and `correction_reason`.

**Fix — both sides:**

a) Frontend: wherever this PUT is sent for a pure status change, add `statusOnly: true` to the body.

b) Backend `PUT /api/discharges/:id`: before running the full-overwrite branch, fetch the existing row and fall back to its old values for any field missing from the request body, so a partial payload can never null a column:

```js
app.put('/api/discharges/:id', async (req, res) => {
  const d = req.body;
  try {
    const { rows: old } = await q('SELECT * FROM discharges WHERE id=$1', [req.params.id]);
    const oldD = old[0];
    if (!oldD) return res.status(404).json({ error: 'Discharge not found' });

    if (d.statusOnly) {
      await q('UPDATE discharges SET status=$1 WHERE id=$2', [d.status, req.params.id]);
    } else {
      const truck            = d.truck            ?? oldD.truck;
      const wasteType        = d.wasteType         ?? oldD.waste_type;
      const gross            = d.gross             ?? oldD.gross;
      const tare              = d.tare             ?? oldD.tare;
      const net               = d.net              ?? oldD.net;
      const unitPrice         = d.unitPrice         ?? oldD.unit_price;
      const total             = d.total             ?? oldD.total;
      const status            = d.status            ?? oldD.status;
      const payMethod         = d.payMethod         ?? oldD.pay_method;
      const siteId            = d.siteId            ?? oldD.site_id;
      const ts                = d.ts                ?? oldD.ts;
      const correctionReason  = d.correctionReason  ?? oldD.correction_reason ?? '';
      const opType            = d.opType            ?? oldD.op_type ?? 'treatment';

      await q(
        `UPDATE discharges SET truck=$1,waste_type=$2,gross=$3,tare=$4,net=$5,
         unit_price=$6,total=$7,status=$8,pay_method=$9,site_id=$10,ts=$11,
         correction_reason=$12,op_type=$13 WHERE id=$14`,
        [truck, wasteType, gross, tare, net, unitPrice, total, status,
         payMethod, siteId, ts, correctionReason, opType, req.params.id]
      );
      // keep existing consumed-adjustment diff logic, but using the resolved
      // `total`/`payMethod` values above, not the raw possibly-undefined d.total/d.payMethod
    }
    ok(res, { ok: true });
  } catch(e) { er(res, e); }
});
```

# PHASE 1 — Schema: add real bill/payment tracking tables

Create a new migration file (following the existing migration pattern in the `migrations` directory) adding these tables. This is the foundation for everything in Phase 3.

```sql
-- A "bill" is an explicit, scoped snapshot of discharges owed at the time it's generated.
-- It is NOT the same as the existing `invoices` table's month-based aggregation — a bill
-- can cover an arbitrary set of discharges (e.g. "everything unbilled as of today").
CREATE TABLE IF NOT EXISTS bills (
  id            VARCHAR(30) PRIMARY KEY,
  client_id     VARCHAR(10) NOT NULL REFERENCES clients(id),
  generated_at  TIMESTAMP DEFAULT NOW(),
  total_ht      DECIMAL(12,2) NOT NULL,
  total_ttc     DECIMAL(12,2) NOT NULL,
  status        VARCHAR(20) DEFAULT 'open',  -- open | partial | paid
  note          TEXT
);

-- Explicit scope: which discharges belong to which bill. A discharge can appear in
-- at most one OPEN bill at a time (enforce in application logic, not just DB).
CREATE TABLE IF NOT EXISTS bill_discharges (
  id            SERIAL PRIMARY KEY,
  bill_id       VARCHAR(30) NOT NULL REFERENCES bills(id) ON DELETE CASCADE,
  discharge_id  VARCHAR(20) NOT NULL REFERENCES discharges(id),
  UNIQUE(bill_id, discharge_id)
);

-- Raw payment event — what the client actually handed over, before allocation.
CREATE TABLE IF NOT EXISTS payments (
  id            VARCHAR(30) PRIMARY KEY,
  client_id     VARCHAR(10) NOT NULL REFERENCES clients(id),
  bill_id       VARCHAR(30) REFERENCES bills(id),
  amount_ttc    DECIMAL(12,2) NOT NULL,
  method        VARCHAR(20),
  note          TEXT,
  created_at    TIMESTAMP DEFAULT NOW(),
  created_by    VARCHAR(10) REFERENCES users(id)
);

-- The allocation ledger: exactly how much of each discharge was settled by each payment.
-- This is the source of truth for "how much of discharge X has been paid" — never a
-- manually-incremented column on the discharge itself.
CREATE TABLE IF NOT EXISTS discharge_payments (
  id                SERIAL PRIMARY KEY,
  discharge_id      VARCHAR(20) NOT NULL REFERENCES discharges(id),
  payment_id        VARCHAR(30) NOT NULL REFERENCES payments(id) ON DELETE CASCADE,
  bill_id           VARCHAR(30) NOT NULL REFERENCES bills(id),
  applied_amount_ttc DECIMAL(12,2) NOT NULL,
  applied_amount_ht  DECIMAL(12,2) NOT NULL,
  applied_qty        DECIMAL(10,3) NOT NULL,
  created_at         TIMESTAMP DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_discharge_payments_discharge ON discharge_payments(discharge_id);
CREATE INDEX IF NOT EXISTS idx_bill_discharges_bill ON bill_discharges(bill_id);
CREATE INDEX IF NOT EXISTS idx_discharges_client_ts ON discharges(client_id, ts);
```

A discharge's **remaining balance** is always computed live, never stored:
```sql
remaining_ttc = discharge.total_ttc - COALESCE((
  SELECT SUM(applied_amount_ttc) FROM discharge_payments WHERE discharge_id = discharge.id
), 0)
```
(`total_ttc` = `total * 1.19` if the client is `vatSubject`, else `total`.)

# PHASE 3 — Scoped FIFO partial-payment and bill-splitting engine

This is the core feature. Implement exactly this behavior, validated against the worked test case at the end of this phase.

## 3.1 — Bill generation

A new endpoint `POST /api/bills` takes `{ clientId }` and:
1. Finds every discharge for that client that is **not already scoped to an open/partial bill** and has `remaining_ttc > 0` (per the live computation in Phase 1), ordered by `ts ASC`.
2. Creates a new `bills` row with `total_ht`/`total_ttc` summed from those discharges' remaining amounts.
3. Inserts one `bill_discharges` row per discharge included.
4. Returns the new bill with its scoped discharge list.

A discharge must never be pulled into more than one **open** bill at a time — enforce this with the uniqueness of "not already in an open/partial bill" in the selection query (e.g. `NOT EXISTS (SELECT 1 FROM bill_discharges bd JOIN bills b ON b.id=bd.bill_id WHERE bd.discharge_id = d.id AND b.status IN ('open','partial'))`).

## 3.2 — Applying a payment (the FIFO waterfall)

New endpoint `POST /api/bills/:billId/payments` takes `{ amountTTC, method, note, createdBy }`. Inside a single DB transaction with row locks on the bill and its discharges:

1. Convert `amountTTC` to integer centimes: `P_c = Math.round(amountTTC * 100)`.
2. Fetch the bill's discharges (via `bill_discharges` join `discharges`) **ordered by `ts ASC, discharge_id ASC`** (tiebreaker), each with its live `remaining_ttc` computed as in Phase 1, locked `FOR UPDATE`.
3. For each discharge in that order:
   - `due_c = round(remaining_ttc * 100)`
   - if `due_c <= 0`: skip (already fully paid)
   - if `P_c <= 0`: stop — no more payment left
   - `applied_c = Math.min(P_c, due_c)`
   - Convert `applied_c` back to `appliedTTC`, then `appliedHT = client.vatSubject ? appliedTTC / 1.19 : appliedTTC`
   - `appliedQty = appliedHT / discharge.unitPrice`
   - Insert a `discharge_payments` row: `{discharge_id, payment_id, bill_id, applied_amount_ttc: appliedTTC, applied_amount_ht: appliedHT, applied_qty: appliedQty}`
   - `P_c -= applied_c`
4. If `P_c > 0` after the loop (overpayment beyond this bill's total): do NOT auto-create a credit balance. Return the leftover amount in the response as `unappliedAmount` so the admin sees it and decides what to do (refund, apply to next bill manually, etc.) — this must be a value the frontend surfaces to the admin, not silently dropped.
5. Insert one `payments` row recording the raw amount actually applied (`amountTTC - unappliedAmount`).
6. Recompute the bill's status: `paid` if all its discharges now have `remaining_ttc = 0`, else `partial`.
7. Commit.

## 3.3 — Payment receipt generation (grouped by waste type)

After a payment is applied, generate the receipt from **only the `discharge_payments` rows just created by this payment** (not the whole bill, not the client's whole history):

```
group these discharge_payments rows by waste_type
for each group:
  totalAppliedHT = sum(applied_amount_ht in group)
  unitPrices = distinct unit prices of the discharges in this group
  if unitPrices.length === 1:
    line.qty = totalAppliedHT / unitPrices[0]
    line.unitPrice = unitPrices[0]
  else:
    // mixed tariffs within the same waste type in this one payment — do not
    // fabricate a single clean unit price/qty. Show the montant only, and
    // flag this line as "tarifs multiples" so the admin sees it's a blend,
    // OR list it as separate sub-lines per unit price. Implement as separate
    // sub-lines per unit price (cleaner, still traceable) rather than a fake average.
  line.montant = totalAppliedHT (or TTC per how the bill displays, matching existing invoice display convention)
```

Total of all lines must exactly equal `amountTTC - unappliedAmount` from 3.2 — assert this in code (throw/log if it doesn't match, as a correctness guard) since any mismatch means a bug in the allocation.

## 3.4 — Next-bill generation (remaining balance rollover)

When `POST /api/bills` (3.1) is called again for the same client later, it must naturally pick up:
- Any discharge with `remaining_ttc > 0` that was partially paid in a previous bill (its remaining balance carries forward automatically since it's computed live from `discharge_payments`, not stored) — no special "carry forward" logic needed beyond the live remaining-balance computation itself.
- Any new discharges created since the last bill, that aren't yet in any open/partial bill.

Group the new bill's line items by waste type using the same `groupByType` logic from 3.3, but instead of `applied_amount_ht` per group, use each discharge's **remaining amount** (in centimes, same precision rules).

# PHASE 3B — Unified three-strategy payment engine (by discharge / by amount / full payment) + per-discharge payment visibility

This builds directly on Phase 3's engine and tables. Do not proceed to this phase until Phase 3.5's test case passes exactly.

## 3B.1 — One shared payment engine, three selection strategies

Do not build three separate payment flows. Build **one** payment modal with a three-way toggle for *how the admin selects what to pay*; all three strategies must produce the exact same internal shape (a "plan": a list of `{dischargeId, appliedTTC}`), which then flows through one identical generate-bill → confirm-payment pipeline (3B.3). This is required — do not let any of the three options skip the bill-generation step or use a different commit path.

- **"Par décharge spécifique"** — admin checks specific discharge(s) from the bill's list; the plan is simply "fully settle each checked discharge."
- **"Montant libre"** — admin types any DA amount; the plan is computed by the FIFO waterfall (3B.2) starting from the oldest unpaid discharge in the bill.
- **"Paiement intégral"** — a single-click shortcut that is exactly the "Montant libre" path with the amount pre-filled and locked to the bill's full current remaining total (`SUM(remaining_ttc)` across the bill's discharges) — same waterfall, same code path, it simply happens to fully settle every discharge in the bill because the amount covers everything.

All three must write through the same `payments` / `discharge_payments` ledger, and all three must go through the identical two-step generate-then-confirm flow in 3B.3 — none of them is allowed to commit a payment without a bill document having been generated first for that exact plan.

## 3B.1b — Unify the preview endpoint to accept any of the three selection strategies

`POST /api/bills/:billId/payments/preview` (3B.2) must accept **either** an amount **or** an explicit discharge selection, and internally normalize both into the same allocation-plan shape before returning:

```
Body (Montant libre / Paiement intégral): { amountTTC }
Body (Par décharge spécifique):           { dischargeIds: ["d1","d2",...] }
```
For the discharge-ID case, build the plan by fully settling each named discharge (using its live `remaining_ttc`) — no FIFO walking needed, the admin already chose exactly what to pay. For the amount case, run the FIFO waterfall as already specified. Both paths must return the identical response shape (`lines`, `unappliedAmount`, `receiptByType`, `totalApplied`) so the frontend's bill-generation step (3B.3) never needs to know which selection strategy produced the plan.

## 3B.2b — Tonnage vs. rotation: how a touched discharge renders on the bill line

The waterfall in 3B.2 never special-cases rotation discharges — it applies money to them in FIFO order exactly like tonnage discharges. **What differs is only how the receipt line displays quantity**, because a rotation is one atomic truck pass that either happened or didn't — it cannot be fractionally represented, unlike tonnage which is a continuous, genuinely divisible physical quantity.

For each discharge touched by the allocation, check `discharge.payMethod`:

**If tonnage-billed** (`payMethod !== 'rotation'`):
```
equivQty = appliedHT ÷ unitPrice     // a fractional quantity here is physically meaningful
```
Unchanged from the original spec.

**If rotation-billed** (`payMethod === 'rotation'`):
```
qty = 1                              // always the real, whole rotation count for this discharge row
                                      // — NEVER derived from the applied amount, NEVER fractional
montant = appliedAmountThisPayment   // whatever portion of the flat per-rotation price this
                                      // specific payment covers — can be less than unitPrice
```

### Grouping/merging rule (extends the existing mixed-tariff rule from 3B.3/A.3)

When building `receiptByType`, group entries by `(wasteType, billingMode)`:

- **Tonnage entries**: merge into one line when unit price matches across the touched discharges (existing rule — sum `equivQty`, sum `montant`). If unit prices differ, split into separate sub-lines per price, same as already specified.
- **Rotation entries**: merge multiple discharges of the same waste type into one aggregate line (`qty = count of discharges`, `montant = sum of applied amounts`) **only if every one of those discharges was fully paid by this payment** (`applied === unitPrice` for each, i.e. `qty × unitPrice === montant` holds exactly). The moment a rotation discharge is only partially covered by this payment, it must be kept as its **own explicit, unmerged line**, tagged `partial: true` with a clear note like `"1 rotation — 600 DA réglés sur 1 500 DA dus"` — never folded into an aggregate count, since that would hide which specific rotation still has money owed on it.

This is a rendering-only rule — it changes nothing about how money is applied or how `remaining_ttc` is computed (that ledger math in Phase 3/3B stays identical for both billing types). It only changes how the `receiptByType` array is built before being handed to the bill-document generator in 3B.3.
